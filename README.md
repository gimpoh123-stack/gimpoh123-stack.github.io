# project_1: 김포 지역 음식점 및 메뉴 추천 서비스

## 1. 프로젝트 개요

이 프로젝트는 사용자가 "오늘 뭐 먹지?"라는 고민을 빠르게 해결할 수 있도록 돕는 김포 지역 기반 음식점 및 메뉴 추천 웹 서비스이다.

사용자는 음식 종류, 가격대, 지역, 식사 상황, 메뉴 성향 같은 조건을 선택할 수 있고, 서비스는 조건에 가장 잘 맞는 음식점과 대표 메뉴를 우선순위에 따라 보여준다. 조건을 선택하지 않은 경우에는 랜덤 추천으로 빠르게 후보를 제공한다.

초기 버전은 별도 서버 없이 동작하는 정적 웹사이트로 구현하며, GitHub Pages 배포를 목표로 한다.

## 2. 문제 정의

사용자는 식사 메뉴를 고를 때 다음과 같은 불편을 겪는다.

- 선택지가 많아 무엇을 먹을지 결정하기 어렵다.
- 음식점 정보는 있어도 대표 메뉴와 가격 정보를 한눈에 보기 어렵다.
- 지도, 검색, 리뷰 사이트를 여러 번 오가며 확인해야 한다.
- 가격대, 음식 종류, 지역, 식사 상황 같은 조건을 반영한 추천을 받기 어렵다.
- 데이터가 적을 때 조건에 맞는 결과가 없으면 서비스가 빈 화면처럼 느껴질 수 있다.

따라서 사용자가 간단한 조건만 선택해도 조건에 최대한 부합하는 후보를 우선적으로 보여주고, 정확히 맞는 결과가 없을 때도 대체 후보를 제공하는 서비스가 필요하다.

## 3. 서비스 목표

초기 목표는 대규모 맛집 플랫폼이 아니라 실제 사용 가능한 작은 추천 웹앱을 완성하는 것이다.

- 김포 지역 음식점과 메뉴 데이터를 정리해 제공한다.
- 사용자가 선택한 조건에 최대한 부합하는 음식점 또는 메뉴를 점수 기반으로 추천한다.
- 조건이 없을 때는 랜덤 추천으로 빠르게 후보를 제시한다.
- 조건에 맞는 결과가 0건이어도 대체 추천을 제공한다.
- 메뉴, 가격, 음식 종류, 지역, 태그, 지도 링크, 검색 링크, 설명을 결과 카드에 표시한다.
- 이미지 용량 제약을 고려해 많은 이미지를 저장하지 않아도 사용할 수 있는 구조를 만든다.
- 별도 서버 없이 HTML, CSS, JavaScript, JSON만으로 동작하게 만든다.
- GitHub Pages에 바로 배포 가능한 구조로 만든다.

## 4. 핵심 기능

### 4.1 랜덤 추천

사용자가 조건을 선택하지 않고 추천 버튼을 누르면 등록된 음식점 또는 대표 메뉴 중 하나를 무작위로 추천한다.

사용 목적:

- 결정이 어려울 때 빠르게 후보를 제시한다.
- 조건 입력 없이도 서비스를 바로 사용할 수 있게 한다.
- 조건 추천 결과가 부족할 때 대체 후보로 활용한다.

### 4.2 조건 기반 추천

사용자가 조건을 선택하면 각 음식점 데이터와 조건을 비교해 점수를 계산한다. 점수가 높은 결과를 먼저 보여준다.

초기 필터 조건:

- 음식 종류: 한식, 중식, 일식, 양식, 분식, 카페, 기타
- 가격대: 저렴함, 보통, 든든한 식사
- 지역: 장기동, 구래동, 사우동, 풍무동, 운양동, 고촌읍, 통진읍, 마산동 등 김포 주요 지역
- 식사 상황: 혼밥, 친구와 식사, 가족 외식, 데이트
- 메뉴 성향: 매운 음식, 국물 음식, 든든한 음식, 가벼운 음식

### 4.3 추천 결과 카드

추천 결과는 카드 형태로 보여준다.

카드에 포함할 정보:

- 음식점 이름
- 대표 메뉴
- 메뉴 가격
- 음식 종류
- 지역
- 추천 태그
- 조건 일치 정도
- 간단한 설명
- 지도 링크
- 추가 검색 링크
- 이미지 또는 이미지 대체 표시

## 5. 추천 알고리즘 설계

### 5.1 기본 방향

추천 알고리즘은 단순 필터링만 사용하지 않는다. 조건이 많을수록 모든 조건을 완전히 만족하는 결과가 줄어들기 때문에, 각 후보에 점수를 부여하고 점수가 높은 순서대로 보여준다.

즉, "모든 조건을 만족하지 않으면 제외"하는 방식이 아니라 "선택한 조건에 얼마나 가까운지 계산해서 정렬"하는 방식이다.

### 5.2 점수 계산 기준

각 음식점은 사용자가 선택한 조건과 비교해 추천 점수를 얻는다.

예상 점수 기준:

- 음식 종류가 일치하면 `+4점`
- 지역이 일치하면 `+3점`
- 가격대가 일치하면 `+3점`
- 식사 상황 태그가 일치하면 태그당 `+2점`
- 메뉴 성향 태그가 일치하면 태그당 `+2점`
- 대표 메뉴 이름이나 설명에 검색어가 포함되면 `+2점`

조건별 가중치를 다르게 두는 이유는 음식 종류, 지역, 가격대처럼 사용자의 선택 의도에 직접적인 조건을 더 중요하게 반영하기 위해서이다. 태그는 보조 조건으로 사용한다.

### 5.3 추천 과정

추천 버튼을 눌렀을 때의 처리 과정은 다음과 같다.

1. 사용자가 선택한 조건을 수집한다.
2. 선택된 조건이 없으면 전체 데이터에서 랜덤 추천을 실행한다.
3. 각 음식점 데이터에 대해 조건 일치 점수를 계산한다.
4. 점수가 1점 이상인 후보만 1차 추천 목록에 포함한다.
5. 추천 목록을 점수 높은 순서로 정렬한다.
6. 점수가 같으면 대표 메뉴 가격이 낮은 후보를 먼저 보여준다.
7. 그래도 같으면 무작위 순서를 섞어 매번 같은 결과만 나오지 않게 한다.
8. 상위 결과를 카드 목록으로 보여준다.

### 5.4 조건이 많을 때의 처리

조건이 많을수록 완전 일치 결과가 없을 가능성이 높다. 따라서 다음 기준으로 결과를 단계적으로 완화한다.

1. 1차: 선택한 조건과 하나 이상 일치하는 후보를 점수순으로 보여준다.
2. 2차: 결과 수가 너무 적으면 핵심 조건만 유지한다.
3. 3차: 핵심 조건에 맞는 후보도 없으면 전체 데이터에서 대체 추천을 제공한다.

핵심 조건 우선순위:

1. 음식 종류
2. 지역
3. 가격대
4. 식사 상황
5. 메뉴 성향

예를 들어 사용자가 `한식`, `구래동`, `저렴함`, `데이트`, `매운 음식`을 선택했는데 완전 일치 결과가 없다면, 서비스는 먼저 `한식 + 구래동 + 저렴함`에 가까운 후보를 찾고, 그래도 없으면 `한식` 또는 `구래동`에 맞는 후보를 보여준다.

### 5.5 결과가 0건일 때의 처리

조건에 부합하는 결과가 0건일 때 빈 결과만 보여주지 않는다.

처리 방식:

- "선택한 조건과 정확히 일치하는 결과가 없어요"라는 안내를 표시한다.
- 선택 조건 중 어떤 조건이 결과를 줄였는지 보여준다.
- 조건을 일부 완화한 대체 추천을 보여준다.
- 대체 추천도 없으면 전체 데이터에서 랜덤 후보 3개를 보여준다.
- 사용자가 바로 다시 시도할 수 있도록 `조건 줄이기`, `랜덤 추천`, `초기화` 버튼을 제공한다.

결과 없음 상태의 우선순위:

1. 조건 일부 완화 추천
2. 같은 음식 종류 추천
3. 같은 지역 추천
4. 전체 랜덤 추천

## 6. 데이터 구조

음식점 데이터는 `data.json` 파일에서 관리한다.

예상 데이터 구조:

```json
[
  {
    "id": "gimpo-001",
    "name": "예시식당",
    "area": "구래동",
    "category": "한식",
    "menus": [
      {
        "name": "김치찌개",
        "price": 9000,
        "tags": ["국물", "든든한", "점심"]
      }
    ],
    "priceLevel": "보통",
    "situations": ["혼밥", "친구와 식사"],
    "tags": ["국물", "든든한", "따뜻한"],
    "mapUrl": "https://example.com",
    "searchUrl": "https://example.com",
    "imageType": "category",
    "imageUrl": "",
    "description": "따뜻한 국물 메뉴가 먹고 싶을 때 추천할 만한 식당"
  }
]
```

초기 데이터는 실제 운영 데이터라기보다 기능 검증을 위한 샘플 데이터로 작성한다. 이후 사용자가 직접 수정하기 쉽도록 JSON 구조를 단순하게 유지한다.

## 7. 이미지 용량 제약과 대안

GitHub 저장소와 GitHub Pages 운영을 고려하면 많은 고용량 이미지를 직접 저장하는 방식은 적합하지 않다. 저장소 용량 1GB 권장 기준을 넘지 않도록 이미지 전략을 별도로 둔다.

### 7.1 기본 원칙

- 음식점별 고해상도 이미지를 저장하지 않는다.
- 초기 버전에서는 이미지가 없어도 서비스 사용이 가능해야 한다.
- 이미지는 추천을 보조하는 요소로 두고, 메뉴명, 가격, 태그, 링크 정보를 핵심 정보로 삼는다.

### 7.2 이미지 대안

사용 가능한 대안:

- 음식 종류별 대표 이미지 1장씩만 사용한다.
- 이미지 대신 음식 종류 아이콘 또는 색상 배지를 사용한다.
- 외부 이미지 URL을 `data.json`에 저장하고 직접 파일은 저장하지 않는다.
- 이미지가 없는 음식점은 카테고리별 기본 이미지를 표시한다.
- CSS 그라데이션이나 패턴 배경을 사용해 카드가 비어 보이지 않게 한다.
- 지도 링크와 검색 링크를 제공해 실제 사진은 외부 서비스에서 확인하게 한다.

초기 MVP에서는 `카테고리별 기본 이미지 + 색상 배지 + 외부 검색 링크` 방식을 사용한다. 이 방식은 저장소 용량을 거의 늘리지 않으면서도 화면 완성도를 유지할 수 있다.

### 7.3 권장 구현 방식

초기 구현에서는 다음 구조를 사용한다.

- `images/korean.jpg`
- `images/chinese.jpg`
- `images/japanese.jpg`
- `images/western.jpg`
- `images/snack.jpg`
- `images/cafe.jpg`
- `images/default.jpg`

이미지를 직접 넣기 어렵거나 용량을 더 줄여야 할 경우, 위 파일도 생략하고 CSS 기반 플레이스홀더를 사용한다.

이미지 표시 우선순위:

1. 음식점에 직접 지정된 `imageUrl`
2. 음식 종류별 기본 이미지
3. CSS 플레이스홀더

## 8. 기술 구성

- `index.html`: 페이지 구조
- `style.css`: 화면 디자인과 반응형 레이아웃
- `script.js`: 랜덤 추천, 조건 점수 계산, 결과 렌더링
- `data.json`: 음식점 및 메뉴 데이터
- GitHub Pages: 정적 사이트 배포

서버, 데이터베이스, 로그인 기능은 초기 버전에 포함하지 않는다.

## 9. 화면 구성

초기 화면은 별도의 홍보용 랜딩 페이지가 아니라 바로 사용할 수 있는 추천 도구로 구성한다.

주요 영역:

- 상단: 서비스 이름과 간단한 소개
- 필터 영역: 음식 종류, 가격대, 지역, 상황, 메뉴 성향 선택
- 액션 영역: 조건 추천, 랜덤 추천, 초기화 버튼
- 결과 영역: 추천 음식점 카드 목록
- 결과 없음 영역: 조건 완화 안내와 대체 추천
- 하단: 데이터 기준과 GitHub Pages 정적 서비스 안내

## 10. 사용자 흐름

1. 사용자가 웹사이트에 접속한다.
2. 원하는 조건을 선택하거나 아무 조건도 선택하지 않는다.
3. 추천 버튼 또는 랜덤 추천 버튼을 누른다.
4. 서비스가 각 음식점의 조건 일치 점수를 계산한다.
5. 점수가 높은 음식점과 메뉴를 우선순위대로 보여준다.
6. 조건에 맞는 결과가 없으면 조건 완화 추천 또는 랜덤 추천을 보여준다.
7. 사용자는 결과 카드에서 메뉴, 가격, 위치, 링크를 확인한다.
8. 마음에 들지 않으면 다시 추천을 받거나 조건을 바꾼다.

## 11. 초기 구현 범위

이번 MVP에서 구현할 범위:

- 김포 음식점 샘플 데이터 8개 이상
- 랜덤 추천
- 음식 종류, 가격대, 지역, 태그 기반 점수 추천
- 조건이 많을 때 점수순 정렬
- 결과 0건일 때 조건 완화 추천
- 결과 카드 렌더링
- 외부 지도 및 검색 링크
- 이미지 대체 표시
- 모바일 대응 CSS

이번 MVP에서 제외할 범위:

- 실제 위치 기반 거리 계산
- 로그인 및 개인화
- 즐겨찾기 저장
- 리뷰 작성
- 관리자 화면
- 실시간 데이터 수집
- 음식점별 고해상도 이미지 대량 저장

## 12. 개발 단계

### 1단계: 기본 페이지 제작

- `index.html`, `style.css`, `script.js`, `data.json` 파일 생성
- 기본 화면 구성
- 샘플 데이터 작성

### 2단계: 추천 알고리즘 구현

- 조건 수집 기능 구현
